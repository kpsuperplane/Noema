# Packet 05: Work UI

**Mode:** implement
**Goal:** add the Work navigation, routes, Board/List/Needs You/Activity/
Completed views, shared task detail, semantic action UX, and chat-side Work
panel specified in [the Work UI contract](../07-work-ui.md).

This packet owns presentation and client orchestration only. It renders the
GraphQL contract generated by the integrator and never creates a second task
state model or a frontend-only transition path.

## Prerequisites

Before starting, confirm:

- Packet 04 has frozen GraphQL operation names, input/output fields, error
  codes, connection semantics, and workEvents/taskEvents subscription shapes.
- The integrator has generated the corresponding frontend schema/types, or has
  supplied a frozen generated-schema diff for this packet to target.
- Existing AppShell, TanStack route generation, Atryx, StyleX, Apollo client,
  chat detail rail, transcript, and subscription reconnect behavior remain
  available.
- The API returns Personal as the only exposed workspace and provides
  validActions rather than requiring the client to infer action eligibility.

## Interfaces consumed and produced

### Consumes

The UI consumes only generated GraphQL fields and semantic mutations:

- workOverview, projects, workTasks, task, needsYou, workActivity,
  completedTasks, and taskRunItems;
- create/update/archive/reopen project and capture/update-Inbox/queue/answer/
  retry/accept/request-changes/cancel/reopen task mutations;
- workEvents and taskEvents cursor subscriptions;
- stage, currentRun, activeGate, latestReview, attention, revision, generation,
  validActions, bounded connections, event cursor, and stable error codes.

No component reads task state from transcript text, notification wording,
provider stream state, or an old status field.

### Produces

This packet delivers:

- route-safe Work home and deep task-detail navigation;
- Board, List, Needs You, Activity, and Completed projections;
- a route-backed project/filter/search state model;
- semantic action forms that supply expected revision, generation, and
  clientMutationId;
- shared task summary/detail primitives used from Work and chat;
- a compact chat-side active-work/Needs You panel and card drill-ins;
- accessible loading, empty, error, stale, reconnect, and responsive states.

## Implementation checklist

### 1. Add routing and shell navigation

- [ ] Add the Work route and deep task route using the existing TanStack file
      route convention. Validate Work tab and filter search parameters at the
      route boundary.
- [ ] Extend AppRoute/AppPath and shell navigation/breadcrumb behavior with
      Work. Keep Personal implicit and preserve the existing Settings back
      behavior.
- [ ] Add a Work page shell that retains filters/tab state when opening and
      closing a deep task detail route.
- [ ] Use the generated route tree; do not edit routeTree.gen.ts. Hand its
      generated diff to the integrator.

### 2. Add GraphQL documents and data hooks

- [ ] Create focused Work operations for overview, list pages, detail
      connections, project controls, all semantic commands, and both event
      streams. Keep generated types as the only client-facing type source.
- [ ] Build Work data hooks that map only presentational concerns such as
      timestamp formatting and safe event labels. Do not create a local
      TaskStatus or execution-phase enum.
- [ ] Use one root workEvents cursor per mounted Work workspace and filtered
      taskEvents only for an open detail/chat rail.
- [ ] Refetch affected bounded queries on committed event receipt and after
      reconnect rather than reproducing stage transitions in Apollo cache.
- [ ] Persist/reuse cursors per workspace/task while mounted and deduplicate
      at-least-once event delivery by event id/cursor.

### 3. Build the Work shell and project controls

- [ ] Implement the route-backed tablist, page toolbar, project filter,
      search, New task capture form, project create/rename/archive/reopen
      controls, and Work status live region.
- [ ] New task creates only an Inbox task with title, description, optional
      explicit project, and client mutation id. Do not expose models,
      execution policy, agents, capability grants, or project memory controls.
- [ ] Keep archived projects available only in explicit historic contexts.
      Archiving never removes cards, cancels tasks, or changes task stage.
- [ ] Use semantic links for task/project navigation and buttons for commands.

### 4. Implement Board and List

- [ ] Render Board columns from workflow metadata and the activeColumns
      response, preserving display order. The initial five labels are Inbox,
      Queue, Doing, Waiting, and Review.
- [ ] Render cards from TaskSummary with title, project, stage, age/current
      update, nullable current-run chip, attention badges, and server-valid
      actions.
- [ ] Add per-column cursor paging and horizontal labelled columns on narrow
      screens. Do not add drag-and-drop or a generic move mutation.
- [ ] Implement dense List as the same workTasks query with text, project,
      stage behavior, attention, and scope filters. Use a semantic table on
      wide screens and labelled rows on narrow screens.
- [ ] Debounce List/Completed search, reset paging on filter changes, and keep
      filters in the route.

### 5. Implement Needs You, Activity, and Completed

- [ ] Group Needs You items by clarification, approval, recovery, and
      review-ready. Bind Answer and Retry to the exact gate id; Accept and
      Request Changes use the task revision/generation while the server checks
      the current eligible review.
- [ ] Delegate Approval UI to the existing approval surface for the named gate
      instead of building a parallel capability-policy editor.
- [ ] Build a cursor-paginated activity timeline from stable event kinds and
      safe fields. Keep raw JSON in detail-only advanced inspection.
- [ ] Build Completed from terminal TaskConnection rows with completed/
      cancelled filtering and Reopen. Explain that Reopen makes a new Inbox
      cycle rather than restarting a cancelled run.

### 6. Refactor and share task detail

- [ ] Split the existing chat detail panel/query mapper into shared
      generated-type adapters, task summary/detail primitives, action controls,
      evidence sections, and a thin Work/chat container.
- [ ] Replace assumptions about queued/executing/reviewing task status with
      single stage plus currentRun, activeGate, latestReview, attention, and
      validActions.
- [ ] Add sections for current contract, gate/message history, contract
      versions, runs/transcripts, evidence/reviews, artifacts/results, and
      task activity, each with bounded pagination.
- [ ] Render reviewer needs-human and post-answer review attempts as linked
      immutable history entries; do not collapse them into one mutable verdict.
- [ ] Preserve the established transcript renderer and live run-item behavior
      for task runs, but map Planner as a run role rather than a task state.
- [ ] Keep the chat rail compact; expose a clear Open Work route for broad
      management. Reuse identical mutation hooks in chat and Work.

### 7. Implement semantic action UX

- [ ] Queue, Answer, Retry, Accept, Request Changes, Cancel, and Reopen call
      only their corresponding API mutation and pass current revision,
      generation, an exact gate id where required, and clientMutationId.
- [ ] Send a structured Approved/Declined decision with an Approval-gate
      answer. Keep change-request feedback required; expose optional request,
      criteria, and complexity amendments only as typed API fields, never a
      local contract editor.
- [ ] Show only actions returned in validActions. Never derive eligibility from
      an English label, stage key, or current run role.
- [ ] Require text for answers and change requests; preserve draft text if a
      stale conflict occurs.
- [ ] Confirm cancellation because it fences active work. Explain Reopen and
      preserve its historic evidence context.
- [ ] On stale revision/generation, refetch the authoritative task, show a
      clear conflict message, retain form input, and require an explicit
      resubmission.

### 8. Add chat-side Work presentation

- [ ] Add a compact panel to chat that shows bounded active task summaries and
      Needs You items, with one route/link per task.
- [ ] Update transcript cards to show stage plus derived attention/current-run
      summary from the new task projection, not an old task status.
- [ ] Limit chat cards to creation, Waiting, Review-ready, recovery, and
      accepted-completion notifications. Routine Worker progress remains in
      Work/detail.
- [ ] Ensure cards, panel, rail, and Work route use the same shared summary
      and action components where density permits.

### 9. Complete resilience and accessibility work

- [ ] Add skeletons, empty states, filtered-empty state, retained-data query
      errors, neutral unavailable detail, per-action pending state, stale
      conflict recovery, missing configuration link, and reconnect status.
- [ ] Add landmarks, headings, tab roles, labelled forms, focus restoration,
      keyboard action/menu controls, and polite live announcements without
      announcing each worker transcript item.
- [ ] Provide icon-plus-text attention/status cues, reduced-motion behavior,
      keyboard-navigable non-draggable Board columns, and responsive layouts.
- [ ] Keep user-visible Work copy concise and decision-oriented. Do not expose
      provider credentials, raw event JSON, lease internals, or unredacted tool
      payloads.
